# Storm Watch — Score Saturation Diagnosis & Balancing Report

Generated by `tools/make_report.js` from exhaustive runs of every hardware × decision combination (32 designs × 256 decision sequences = 8,192). Nothing in this report is estimated by hand.

Three versions were tested:

1. **Shipped game** (`index.html` before this fix): the game's own `simulate()` / `scoreCard()`.
2. **Spec v3.3 as written**: a new hourly, ledger-based engine implementing §10.10, §13, §14 and §23 exactly.
3. **v3.4 revision**: the same engine with the documented balancing changes below.

## 2. Why players previously received 100/100

**Shipped game.** The game did not implement the specification's simulation at all:
- Science points per challenge came from a fixed lookup table (4.1–5.6 points per challenge, whatever the hardware could physically do). Storm coverage simply added +1 per challenge, so any completed run reached 3–4 phases.
- The battery changed by fixed percentages (−10 for high resolution, −50/−25 in the anomaly, halved for advanced power). The lowest battery ever reached was 30%, so the safe-mode rule (≤10%) and the efficiency penalty (<20%) could never trigger. **Resource Efficiency and Reliability were 20/20 and 10/10 in 100% of runs.**
- The storage overflow check used free space plus a downlink credit, and it was never exceeded in any run (overflow occurred in 0 runs).
- The urgent update was "delivered" whenever a single rate number was ≥ 0.8, which was true except for the Standard downlink + Eco + Standard Comms combination.
- Part masses and costs did not match §23.1 (e.g. 32 GB storage instead of 24 GB, so only 16 of 32 designs were launchable).

**Spec v3.3 as written also saturates** (94% at 100) when implemented faithfully. Root causes found in the exhaustive run:
1. **Collected science is far above the target.** Collected science ranged 13.68–69.3 points (median 29.25) against a 12-point target, and a single global clamp means extra points anywhere fill the bar. Covered phases were never below 3.
2. **Background downlink makes delivery automatic.** Delivered science ranged 9.7–54 (median 18); G1 passed in 94.5% of runs. Delivery had no notion of timeliness, so data delivered 15 hours late counted fully.
3. **The urgent update is guaranteed by the priority rule.** C4 always transmits phase-4 records first, so the critical update was delivered in 99.8% of runs.
4. **avoidableEnergyWaste is structurally zero.** The engine (correctly) defers optional work it cannot finish, so no energy is ever "knowingly" wasted. The data-waste term only rarely triggers. Efficiency was 20/20 in 94.5% of runs.
5. **The power anomaly never threatens the spacecraft.** At 50% solar, the lowest final battery was 62.38% and health stayed at 100 in every run, so C3 had little consequence and Reliability was 10/10 in 100% of runs.

## 3. What changed in v3.4 (and why)

Every change is a centralized constant or formula in `engine.js` (`PROFILES.v34`). The five dashboard metrics, the four report categories (35/35/20/10) and the four mission gates are unchanged.

| # | Change | Engineering / educational reasoning |
|---|---|---|
| 1 | **Timeliness factor on delivered science**: delivered value × 1.00 if latency ≤ 3 h, 0.75 ≤ 6 h, 0.50 ≤ 12 h, 0.25 beyond. "Useful Data Delivered" and gate G1 use this value. | Spec §10.8 already lists "arrives before the scientific deadline" as part of usefulness. Hurricane forecasts are reissued on a roughly 6-hourly advisory cycle, so data older than one cycle has reduced forecast value. Thresholds are educational values. |
| 2 | **Phase-based targets**: Science and Delivery categories use Σ min(1, phase points / 3) over the 4 phases (3 = 12/4) instead of one global clamp. | Rewards temporal coverage through the whole storm. Farming many images in one phase no longer fills the bar. Redundancy rules still apply within each hour. |
| 3 | **Productive-yield efficiency** replaces the avoidable-waste counters: 20 × activity × (0.5 × energy yield + 0.5 × data yield). Energy yield = imaging + comms energy spent on observations that were delivered (timeliness-weighted) ÷ all optional energy. Data yield = delivered GB (timeliness-weighted) ÷ generated GB. | Measures useful science per resource consumed. Energy spent on images that were evicted, never sent or sent stale is unproductive. Keeping the battery high does not earn points, and the activity gate is unchanged. |
| 4 | **C1 Focused Scan**: relevance 0.6 (first) / 0.3 (second scan in an hour) and data size × 0.5. Wide Scan unchanged. | In the development phase the task is to see the storm's structure. A 45% focused scan sees the core but misses the outer bands (lower relevance), and it images half the area, so it produces about half the data. Before this, Focused strictly dominated Wide. |
| 5 | **Power anomaly at 35% of nominal solar** (was 50%). | At 50% the battery never fell below 62.38% in any run, so the C3 learning objective (battery limits operations) had no consequence. At 35%, Standard Power cannot cover the essential load plus a full imaging schedule for 6 hours, and Normal Operations can now exhaust it. No random failure is added: failures arise only from the existing §23.4 rules. |
| 6 | **High-Capacity Comms 0.8 GB/h** (was 1.2). | Sizing rule: the 50% background allocation keeps up only with the economical imaging mode of the matching imager, and full allocation (C4 High-Speed) keeps up with high resolution at routine cadence. At 1.2 GB/h the background link outran every data source, so decisions stopped mattering. |
| 7 | **No pre-emption in the downlink queue**: a file already being transmitted finishes before the next starts. | Real file-based downlinks do not abandon a partly sent file. A large backlog file can now delay the urgent update (head-of-line blocking), so the critical update is no longer guaranteed by the priority rule. |
| 8 | Part masses/costs and 24 GB storage aligned with §23.1 in the game UI. | Bug fix: the shipped UI used different numbers from the spec. |

Unchanged: the 12-point and 3-phase gates, the phase-4 critical-update rule, the 10% reserve, the health/incident and 2-hour failure rules, the 35/35/20/10 weights, and the outcome order (Failure → Success → Partial).

## 5. Honest limits

- **Reliability** is 10/10 in 86.7% of runs. A GEO weather satellite with a protected reserve should rarely lose essential power. Health drops only when Normal Operations exhausts Standard Power during the anomaly. No random failures were added.
- **Science** still reaches 35 in 72.8% of runs: the hardware can easily collect enough, so delivery and efficiency carry most of the differentiation. This matches the mission's core lesson ("collecting is not delivering").
- All thresholds (timeliness bands, 35% anomaly, 0.8 GB/h, focused-scan factors) are **educational game values**, not NOAA/NASA measurements.
- The automated tests (`tools/test_engine.js`) check invariants and release gates. They are not a substitute for playtesting with students.
